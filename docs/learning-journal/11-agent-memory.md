# Phase 8：Agent 结构化记忆与只读资产工具

## 阶段目标

Phase 7 已经让持仓和交易流水跨重启恢复，但当前 `ToolCallingAgent` 的消息仍只保存在进程内，
退出 CLI 后无法继续同一会话。Phase 8 将建立持久化短期会话记忆、用户确认的长期结构化记忆，
并让 Agent 通过只读工具访问资产面板使用的同一 SQLite 数据库。

计划版本：`v0.3.1`。

相关 Issue / PR：Issue #17 / PR 待创建。

## 第一小阶段：记忆领域模型与数据库结构

### 本小阶段目标

- 明确短期会话记忆、长期结构化记忆和资产事实数据的边界；
- 建立会话、消息、记忆条目和记忆事件四类领域模型；
- 新增四张 ORM 表和第二份 Alembic 迁移；
- 使用临时 SQLite 验证迁移循环、UTC 时间、外键和 ACTIVE 记忆唯一约束；
- 不调用百炼、AKShare、GoldAPI，也不迁移开发者的个人数据库。

### 短期记忆为什么也要持久化

“短期”描述的是作用范围，而不是存储介质。短期记忆只服务于一个会话，用于理解代词、恢复近期
消息和保持 assistant 工具请求与 tool 结果的顺序；把它写入 SQLite 后，应用重启仍能继续同一
会话，但其他会话不会默认读取这些消息。

`chat_sessions` 保存会话状态和滚动摘要，`chat_messages` 保存原始消息。摘要通过
`summary_until_sequence` 标记覆盖位置，原始消息不会因为摘要而删除。

### 长期记忆与持仓事实为什么必须分开

长期记忆只保存用户确认的稳定偏好、约束、关注项、目标和反馈。当前持仓数量、基金净值、黄金
价格、浮动收益和交易流水随时间变化，必须继续从 Portfolio、Ledger 和 MarketData 工具读取，
不能复制成容易过期的记忆。这样 Agent 可以“记住用户黄金仓位上限为 30%”，但不能把“当前
持有 1.5 克黄金”当作永久事实。

### 四张表的职责

| 表 | 职责 |
|---|---|
| `chat_sessions` | 会话标题、状态、滚动摘要和摘要覆盖位置 |
| `chat_messages` | user、assistant、tool 消息及工具调用关联字段 |
| `memory_items` | 候选、已生效、被替换、已拒绝和已过期的结构化记忆 |
| `memory_events` | 不保存记忆正文的确认、拒绝、替换、过期和删除审计事件 |

消息表使用 `(session_id, sequence_number)` 唯一约束，防止同一会话出现重复序号。会话删除时
消息随之删除；长期记忆的来源外键使用 `SET NULL`，避免删除聊天历史时偷偷删除用户已经确认的
长期偏好。

### ACTIVE 记忆为什么使用部分唯一索引

同一个范围内，同一 `memory_type + memory_key` 只能有一条 ACTIVE 记忆，否则 Agent 不知道
应该使用“黄金上限 30%”还是“黄金上限 20%”。候选记忆允许同时存在，用户确认新版本时，
MemoryService 会先把旧版本改为 SUPERSEDED，再激活新版本。

SQLite 的唯一约束会把多个 `NULL` 当作不同值，因此全局记忆在 ORM 层把 `scope_id` 统一保存
为空字符串，再使用只针对 `status = 'active'` 的部分唯一索引。领域模型对外仍以 `None` 表达
全局范围，不把数据库实现细节泄漏到业务层。

### 删除记忆后为什么仍保留事件

用户要求删除长期记忆时，`memory_items.value_json` 应被硬删除，避免敏感正文继续存在。审计表
不设置到记忆正文的外键，只保存记忆 UUID、事件类型、操作者和白名单元数据，因此可以证明系统
执行过删除动作，但不能恢复被删除的内容。

## 第二小阶段：Repository 与统一事务

### 本小阶段目标

- 定义 `ConversationRepository` 与 `MemoryRepository` 协议，让上层不依赖 SQLAlchemy；
- 实现会话 CRUD、自动编号的消息追加、消息窗口读取和工具调用 JSON 往返；
- 实现长期记忆新增、组合条件查询、状态更新、硬删除和审计事件追加；
- 使用 `SqlAlchemyMemoryUnitOfWork` 让会话消息、记忆正文和事件一起提交或回滚；
- 使用临时 SQLite 验证重启恢复、ACTIVE 唯一约束、来源解绑和删除审计保留。

### Repository 和 Unit of Work 各自负责什么

Repository 像一个“只会存取某类资料的管理员”：会话仓库只处理会话和消息，记忆仓库只处理
长期记忆和审计事件。它们会把 ORM Row 转成严格领域模型，也会把数据库约束错误转换成稳定的
领域异常，但不会自己决定哪些内容值得记忆。

Unit of Work 像一个“整笔操作的总开关”。例如模型提出一条候选偏好时，系统需要同时保存来源
消息、候选正文和 `candidate_created` 事件。三步都成功才调用一次 `commit`；任一步失败，退出
工作单元时全部回滚，数据库不会出现“候选已经存在但找不到来源或审计”的半成品。

### 为什么消息序号由仓库分配

调用 Agent 的代码只知道下一条消息内容，不应该先查询数据库再自己猜序号。会话仓库在同一事务
中读取当前最大序号并加一，Memory Unit of Work Factory 使用进程内异步锁串行化 SQLite 事务，
数据库的 `(session_id, sequence_number)` 唯一约束再作为最后防线。这一设计同时把并发细节挡在
Agent 外面，并保持消息窗口可以按整数序号稳定恢复。

### 为什么记忆事务没有直接合并资产面板事务

记忆和资产面板使用同一个 `DatabaseManager` 与 SQLite 文件，但分别拥有 Memory 和 Dashboard
Unit of Work。候选确认不需要访问持仓仓库，买卖流水也不应意外修改聊天记录。保持两个窄事务
边界能降低模块耦合；下一阶段只读资产工具会在应用服务层组合两类能力，而不是制造一个包含所有
Repository 的“万能事务对象”。

### JSON 如何安全往返

工具调用、结构化记忆值和事件详情包含嵌套数据，因此数据库以 JSON 文本保存。Repository 使用
固定键排序、紧凑分隔符和 UTF-8 中文生成稳定文本；读取时先解析 JSON，再交给 `ToolCall`、
`ConversationMessage`、`MemoryItem` 或 `MemoryEvent` 重新校验。若数据库内容损坏或根节点类型错误，
系统明确抛出 `PersistenceError`，不会用空列表或空对象掩盖数据问题。

## 第三小阶段：MemoryService 状态机与隐私边界

### 本小阶段目标

- 使用不含状态字段的 `MemoryCandidateCreate` 接收模型候选，阻止模型直接生成 ACTIVE 记忆；
- 校验候选必须来源于数据库中真实存在且属于相同会话的 user 消息；
- 实现用户确认、拒绝、同身份冲突替换、TTL 到期和硬删除；
- 使用版本号与 `supersedes_id` 保留完整记忆历史，不静默覆盖旧正文；
- 递归拦截凭据字段和明显敏感标签，并限制审计事件只能写白名单元数据；
- 验证替换中途失败时旧 ACTIVE 和新候选都能通过事务完整回滚。

### 为什么模型只能创建 Candidate

`MemoryCandidateCreate` 故意没有 `status`、`confirmed_at`、`version` 和 `supersedes_id` 字段，而且
Pydantic 配置会拒绝额外字段。模型即使输出 `"status": "active"` 也无法通过命令边界。候选
写入后，只有用户触发的 `confirm_candidate` 才能由确定性 Python 代码填写确认时间并激活。

这相当于把大模型定位成“建议者”，把 Service 定位成“规则执行者”，把用户定位成“最终批准者”。
模型擅长从自然语言中发现可能的偏好，但不能自行决定哪些内容跨会话长期影响之后的回答。

### 冲突记忆如何形成版本链

记忆身份由 `memory_type + memory_key + scope_type + scope_id` 决定。确认同身份新候选时：

1. 在同一 Unit of Work 中读取当前 ACTIVE 与历史版本；
2. 若 ACTIVE 已到 TTL，先迁移为 EXPIRED；否则迁移为 SUPERSEDED；
3. 新候选使用历史最大版本号加一，并通过 `supersedes_id` 指向上一确认版本；
4. 写入替换和确认审计事件；
5. 全部成功才提交，任一步异常则整体回滚。

因此“黄金仓位上限 30%”改为“20%”后，Agent 只读取 version 2，但用户仍可以审计 version 1
的原值、确认时间和退出原因。

### TTL 的精确口径

`ttl_seconds=None` 表示不自动过期，适合稳定风险偏好；正数 TTL 最多一年，适合临时目标或关注项。
当前 TTL 从候选创建的服务端时间开始计算，采用 `expires_at <= now` 作为到期边界。候选已经到期
时不能再确认；ACTIVE 到期后由查询或显式扫描迁移成 EXPIRED，并追加 SYSTEM 审计事件。

TTL 使用可注入时钟，测试通过推进虚拟时间验证 899 秒仍有效、恰好 900 秒立即过期，不需要真的
等待 15 分钟。时钟必须包含时区，也不能早于记忆最近更新时间。

### 敏感字段与审计白名单

服务在构造 ORM 对象之前递归扫描 `memory_key`、嵌套 JSON 键和明显凭据标签，阻止 API Key、
访问令牌、密码、私钥、银行卡、身份证和助记词等字段进入数据库。错误只说明“包含禁止内容”，
不会把命中的值复制进异常或日志。

审计事件不接收模型自由文本，每种事件都有固定字段集合，例如确认只允许版本号和上一记忆 UUID，
删除只允许版本号、删除前状态和 `user_request` 原因代码。即使正文硬删除，事件也无法恢复正文。

## 第四小阶段：持久化会话、滚动摘要与上下文组装

### 本小阶段目标

- 实现会话创建、读取、列表、归档、删除和消息追加应用服务；
- 使用 `ConversationSummarizer` 协议隔离摘要算法，提供统一 ModelProvider 摘要适配器；
- 按完整 user/assistant/tool 轮次选择可摘要前缀，避免切断工具调用协议；
- 摘要模型调用不占用数据库事务，写回时使用乐观冲突检查；
- 组装固定系统提示、ACTIVE 长期记忆、会话摘要和近期原始消息；
- 使用临时 SQLite 和 Fake 验证跨重启恢复、滚动覆盖和资产范围过滤。

### “近期消息数量”为什么是软上限

如果只执行 `messages[-12:]`，切点可能恰好落在 assistant 工具请求和 tool 结果之间。此时模型会
看到没有来源的 tool 消息，OpenAI-compatible 接口可能直接拒绝请求。项目改为先识别完整轮次：
一轮从 user 开始，经过零次或多次 assistant/tool 循环，以 assistant 最终文本结束。

摘要只选择最老的完整轮次。如果一整轮包含 15 条工具消息，而软上限是 12，系统会暂时保留 15
条，也不会破坏工具调用链。复杂 Token 预算和语义压缩仍留待后续专门阶段。

### 滚动摘要为什么分成两个短事务

摘要可能需要几秒模型调用。如果在 `async with UnitOfWork` 中等待模型，SQLite 写入锁和进程内锁
会被长时间占用，其他会话无法追加消息。现在流程为：

1. 第一个短事务读取旧摘要和待摘要完整轮次，然后立即关闭；
2. 在事务外调用 Fake 或真实摘要模型；
3. 第二个短事务重新读取会话；
4. 若摘要内容或 `summary_until_sequence` 已被其他任务改变，拒绝旧结果；
5. 否则写入新摘要和覆盖序号。

摘要期间新追加普通消息不会造成冲突，因为本次结果只覆盖已经固定的旧序号；只有另一摘要任务
推进同一摘要版本时才需要拒绝覆盖。

### 摘要与长期记忆有什么区别

滚动摘要只压缩当前会话早期内容，可能包含本次讨论过程、工具结果和未解决问题。它不会跨会话
默认使用，也不代表用户确认了其中每句话。长期记忆只保存用户确认的稳定偏好、约束、关注项、
目标和反馈，并受状态机、版本、TTL 和删除规则管理。

上下文组装时二者使用两个独立 system 数据块，并明确标注它们只是背景事实而不是新的系统指令。
摘要覆盖位置之后才追加原始消息，因此同一内容不会以“摘要 + 原文”重复进入模型。

### 资产范围记忆如何控制注入

`ContextAssembler` 默认只注入全局 ACTIVE 记忆。调用方显式传入 `017811` 后，才增加该基金范围
记忆；`JD-ZS-GOLD` 的约束不会因为它也在数据库里就进入本次上下文。这样可以减少无关信息，
也为下一阶段根据只读资产工具结果动态决定相关代码留下清晰接口。

## 第五小阶段：持久化 Agent 编排与整轮事务

### 本小阶段目标

- 新增 `PersistentToolCallingAgent`，把持久化上下文接入已有的模型—工具—模型循环；
- 一轮成功后原子保存 user、assistant 工具请求、tool 结果和最终 assistant 回答；
- 模型连接失败、步数超限或数据库提交失败时，不留下任何本轮残缺消息；
- 工具参数错误作为结构化 tool 消息返回模型，模型成功纠正后再保存完整纠错轨迹；
- 同会话请求在进程内串行执行，并使用会话更新时间阻止跨进程的过期上下文写回；
- 使用临时 SQLite、Fake ModelProvider 和本地确定性工具验证跨重启恢复与故障回滚。

### 一轮 Agent 对话为什么不能逐条写数据库

Agent 的一轮对话不一定只有“用户问题 + 最终回答”，还可能是：

```text
user
  → assistant(tool_calls)
  → tool(result)
  → assistant(tool_calls)
  → tool(result)
  → assistant(final answer)
```

如果每产生一条就立即提交，第二次模型请求断网时，数据库会只剩 user、assistant 工具请求和
tool 结果。下一次恢复会话时，这组消息没有最终回答，既难以向用户解释，也可能让模型误以为上轮
仍在执行。现在 Agent 先用 `working_messages` 在内存中完成推理，同时用 `turn_messages` 只收集
本轮增量；得到最终回答后才调用 `ConversationService.commit_turn`。

`commit_turn` 先校验消息确实是一个完整轮次，然后在同一个 Memory Unit of Work 中逐条 flush、
最后只 commit 一次。任意消息失败会触发 `__aexit__` 回滚，因此已经 flush 的前几条也不会残留。
system prompt、长期记忆数据块、摘要和旧消息只属于模型上下文，绝不会被当作本轮增量重复写库。

### 工具错误为什么有时保存、有时不保存

模型生成错误参数是 Agent 可以自我纠正的正常分支。`ToolValidationError`、未知工具等 `ToolError`
会被转换成 `{"ok": false, ...}` 的 tool 消息交给模型：

- 模型随后给出最终解释或改用正确参数：整轮成功，错误轨迹与最终回答一起保存；
- 模型随后网络失败或始终无法结束：整轮失败，user、tool 错误和中间消息全部不保存。

因此数据库记录的是“已完整结束的对话事实”，而不是只记录成功工具结果或把每个工具错误都当成
系统崩溃。未来工具仍会限制为只读资产查询，避免在最终消息提交前产生不可回滚的外部副作用。

### 为什么同时需要会话锁和更新时间检查

同一进程内，Agent 为每个 `session_id` 保存一个 `asyncio.Lock`。两个请求同时访问同一会话时，
后一个必须等前一个完成，所以它组装上下文时能看到前一轮最终回答；不同会话的请求不互相阻塞。

进程内锁无法约束另一个应用进程。为此上下文组装时记录 `session.updated_at`，提交前再次读取当前
会话并比较：如果推理期间历史已变化，系统抛出 `ConversationConflictError`，拒绝把基于旧上下文
生成的回答接到新历史后面。这属于乐观并发控制，数据库消息序号唯一约束仍是最后一道防线。

### `PersistentAgentTurnResult` 提供什么

成功调用不只返回回答字符串，还返回本轮持久化消息、模型调用次数和按顺序执行的工具名。这些
字段让后续 Web/CLI 可以展示回答，也为 Agent 评测、调用链审计和可观测性提供确定数据；它不包含
system prompt、长期记忆正文或数据库内部事务对象。

## 第六小阶段：SQLite 只读资产工具

### 本小阶段目标

- 新增组合快照、单项持仓和交易账本摘要三个 Agent 工具；
- 工具只依赖 Dashboard 与 Ledger Service 的读取协议，不直接访问 SQLAlchemy；
- 使用独立注册工厂形成只读白名单，不混入买入、卖出、修改或删除入口；
- 金融数值保持 Decimal 字符串，组合估值继续复用 PortfolioCalculator；
- 账本结果删除 UUID、内部创建时间和自由文本备注，减少发送给云模型的数据；
- 通过持久化 Agent 集成测试验证真实工具结果和完整 tool 消息能够写入 SQLite。

### 三个工具分别解决什么问题

| 工具 | 数据来源 | 适合回答的问题 | 明确不做什么 |
|---|---|---|---|
| `get_portfolio_snapshot` | `PortfolioDashboardService.get_dashboard()` | 当前市值、毛净收益、仓位、HHI、行情时间与质量 | 不新增持仓、不交易 |
| `get_holding_record` | `PortfolioDashboardService.get_holding()` | 指定资产的数量、均价、预计卖出费率 | 不查询行情、不修改记录 |
| `get_transaction_ledger_summary` | `TransactionService.list_transactions()` | 流水数量、买入支出、卖出到账、费用、已实现收益、最近流水 | 不试算或确认卖出 |

持仓记录与组合快照故意拆开：前者只读 SQLite 中稳定的数量和成本，后者才访问行情并运行估值。
如果用户只问“持有多少份”，模型不需要为此查询外部市场；如果用户问“现在浮盈多少”，必须调用
组合工具，不能把旧对话中的价格当成当前行情。

### 只读是怎样保证的

只读不是依靠提示词要求模型“自觉”，而是使用三层代码边界：

1. `PortfolioReadService` 和 `LedgerReadService` 协议只声明读取方法；
2. `create_read_only_asset_tool_registry` 只注册三个 `get_*` 工具，模型无法按名称动态调用 Service；
3. 自动测试在调用全部工具前后比较持仓和完整流水，确认 SQLite 状态完全一致。

当前工具可能查询 Fake/Real 行情，因此“只读”表示不修改用户业务状态，不表示永远没有网络请求。
自动测试固定使用 Fake Provider；真实模式下组合快照仍遵守已有 AKShare、GoldAPI 和手工金价规则。

### 为什么账本工具不原样返回 ORM 或完整领域对象

工具结果随后会进入模型上下文。交易 UUID、数据库 `created_at` 和用户自由文本备注不是回答持仓
问题的必要信息，原样发送会增加 Token、暴露内部结构，也可能把备注中的私人信息交给云模型。
工具因此只返回代码、类型、数量、价格、金额、费用、已实现收益、币种和业务发生时间。

最近流水最多返回 20 条；汇总使用一次 `list_transactions` 的不可变结果计算，避免读取流水与读取
已实现收益之间插入另一笔交易而产生前后不一致。所有金额使用 Decimal 求和并转换为两位字符串，
不会引入 JSON float 误差。

## 本阶段问题记录

### 1. Alembic check 认为唯一约束被删除后又新增

- 问题现象：迁移可以成功升级，但 `alembic check` 报告移除
  `uq_chat_messages_session_sequence` 并新增 `session_sequence`。
- 产生原因：ORM 显式填写了简写约束名 `session_sequence`，迁移文件使用项目命名约定生成的完整
  名称；两者约束字段相同，但 Alembic 按名称判断为两个对象。
- 排查思路：读取 autogenerate diff，确认没有字段或唯一性差异，只存在约束名称差异。
- 解决方法：ORM 同样使用稳定完整名称 `uq_chat_messages_session_sequence`，随后
  `alembic check` 不再产生差异。
- 学到的知识：数据库约束的字段一致还不够，ORM metadata 与迁移文件的名称也必须一致，否则
  后续自动迁移可能生成无意义的删除和重建操作。

### 2. 同一次 add_all 写入父会话和子消息触发外键失败

- 问题现象：测试在同一事务中 `add_all(ChatSessionRow, ChatMessageRow)`，SQLite 先收到消息
  INSERT，因父会话尚不存在而触发外键错误。
- 产生原因：两个 ORM Row 没有定义对象 relationship，只存在表级 ForeignKey；不能依赖
  SQLAlchemy 根据 `add_all` 参数顺序自动安排不同 Mapper 的写入顺序。
- 排查思路：根据失败 SQL 确认先执行的是 `chat_messages` INSERT，再对照 ORM 是否存在
  relationship 依赖。
- 解决方法：测试和后续 Repository 都显式先提交会话，再写入消息；没有为了测试方便增加当前
  业务不需要的 relationship。
- 学到的知识：外键可以保护数据库完整性，但不会自动替应用层设计聚合写入顺序；Repository
  仍需要清楚表达父记录和子记录的创建流程。

### 3. ORM 字符串没有转换为 MemoryActor 枚举

- 问题现象：Repository 初版运行 Ruff 正常，但 mypy 报告构造 `MemoryEvent` 时，`actor` 传入了
  `str`，而领域模型要求 `MemoryActor`。
- 产生原因：ORM 为便于 SQLite 约束检查把枚举保存为字符串；从 Row 回到领域模型时漏掉了显式
  枚举转换。
- 排查思路：定位 mypy 指向的构造参数，对比同一转换函数中的 `MemoryEventType(row.event_type)`。
- 解决方法：统一改为 `MemoryActor(row.actor)`，让非法数据库值在边界处立即失败。
- 学到的知识：静态类型检查可以发现测试数据未必覆盖的边界泄漏；ORM 字符串不是领域枚举，转换
  方向的每个字段都要对称处理。

### 4. 测试辅助函数把 UUID 标注成 object

- 问题现象：18 个目标测试全部通过，但 mypy 报告测试辅助函数传给 `MemoryItem.id` 的参数是
  `object`，不是 `UUID`。
- 产生原因：为了表示“任意生成的 ID”写了过宽的 `object` 类型，运行时虽然传入的都是 UUID，
  静态类型系统却无法证明这一点。
- 排查思路：根据 mypy 行号检查辅助函数签名，而不是修改已经正确的领域模型类型。
- 解决方法：把辅助函数参数精确标注为 `UUID` 并补充对应导入。
- 学到的知识：测试代码也属于受维护的工程代码；过宽类型会削弱 mypy 对测试构造数据的保护。

### 5. git diff --check 显示 LF 将转换为 CRLF 的提示

- 问题现象：`git diff --check` 退出码为 0，但对四个已有文件提示工作区中的 LF 下次可能转换为
  Windows CRLF。
- 产生原因：Windows Git 的行尾转换设置与这些文件当前的工作区行尾形式不同；提示不代表存在
  多余空格、冲突标记或无效补丁。
- 排查思路：同时检查命令退出码和实际输出，确认没有 `trailing whitespace` 等 diff 错误，并且
  不对整个仓库做与本任务无关的行尾重写。
- 解决方法：保留项目当前 Git 行尾策略，本阶段不批量格式化文件；`git diff --check` 实际通过。
- 学到的知识：警告和失败要通过退出码及具体内容区分；为了消除无害提示而改写全仓库会制造大量
  无关 diff，违反外科手术式修改原则。

### 6. MemoryService 测试残留未使用的 uuid4 导入

- 问题现象：21 个目标测试全部通过，但 Ruff 报告 `uuid4` 已导入却没有使用。
- 产生原因：测试初稿准备手工构造 UUID，之后改为复用领域模型默认 UUID，导入没有同步删除。
- 排查思路：根据 Ruff 的 `F401` 行号确认没有任何测试仍引用该名字。
- 解决方法：只删除本次新增测试文件中的无用导入，不格式化或改动其他文件。
- 学到的知识：运行正确不等于代码已经收尾；静态检查能持续清理重构后遗留的小噪声。

### 7. 已过期旧版本可能让新记忆版本号重置

- 问题现象：代码复核发现，若旧 ACTIVE 已先转为 EXPIRED，确认同身份新候选时只查询 ACTIVE，
  可能找不到历史版本，从而把新记忆错误标为 version 1。
- 产生原因：最初把“当前冲突对象”和“版本链上一对象”当成同一个概念；前者只能是 ACTIVE，
  后者还可能是 SUPERSEDED 或 EXPIRED。
- 排查思路：按“激活—到期—再次创建—确认”推演状态序列，发现数据库唯一约束只能保护 ACTIVE
  唯一性，不能自动维护历史版本号。
- 解决方法：确认时查询同身份全部历史，从 ACTIVE、SUPERSEDED、EXPIRED 中选最大版本；新版本
  始终加一并建立 `supersedes_id`，同时新增到期后再次确认的回归测试。
- 学到的知识：状态机中的“当前有效状态”和“最新历史版本”是两个维度，版本链不能只看当前
  ACTIVE 记录。

### 8. 初次读取 Agent 文件时使用了错误的目录单数形式

- 问题现象：读取 `src/finagent/agent/tool_calling.py` 和 `src/finagent/chat/service.py` 时提示路径
  不存在。
- 产生原因：根据模块概念猜测了 `agent/` 和 `chat/`，而项目实际使用复数 `agents/`，基础聊天
  位于 `core/chat.py`。
- 排查思路：使用 `rg --files` 和按类名搜索定位 `ToolCallingAgent`、`ChatSession` 的真实路径。
- 解决方法：改为读取 `src/finagent/agents/tool_calling.py` 与 `src/finagent/core/chat.py`，没有创建
  重复目录或移动既有代码。
- 学到的知识：模块路径属于容易变化的仓库事实，修改前应先搜索文件，而不是只根据类名猜目录。

### 9. TTL 测试数据会在确认瞬间恰好过期

- 问题现象：设计“确认后再过期”的测试时，最初为候选设置 1 秒 TTL，又在确认前推进 1 秒；按
  `expires_at <= now` 规则，该候选会在确认时直接被拒绝，无法形成 ACTIVE 测试前提。
- 产生原因：忽略了 TTL 从候选创建时间开始，而不是从确认时间开始。
- 排查思路：逐步列出创建、确认、上下文组装三个时间点，对照精确到期不等式。
- 解决方法：测试改为 2 秒 TTL，创建后 1 秒确认，再推进 1 秒触发到期。
- 学到的知识：时间测试应先画时间线；边界规则正确时，测试夹具也必须遵守同一业务口径。

### 10. PowerShell 不支持当前写法中的 `&&`

- 问题现象：并行复核仓库时，把多个 Git 命令用 `&&` 拼接交给当前 PowerShell，解析阶段报

- 产生原因：工具当前启动的是较旧 Windows PowerShell，而 `&&` 不是该版本的合法命令分隔符；
  同样的写法在 Git CMD 中可以使用。
- 排查思路：错误发生在任何 Git 输出之前，因此不是仓库或 Git 故障，而是命令解释器语法问题。
- 解决方法：Git 状态复核明确改用 `cmd.exe`，并使用 Git CMD 支持的命令分隔形式。
- 学到的知识：命令本身和执行它的 Shell 是两个边界；给用户的 Git 命令及自动复核都应与约定的
  Git CMD 语法一致。

### 12. `git diff --stat` 不显示未跟踪的新 Agent 文件

### 13. 组合执行提交与推送时提交说明被拆成 pathspec

- 问题现象：把 `git commit -m "..."`、push 和状态复核拼成一次执行时，Git 报告
  `pathspec 'integrate' did not match any file`；提交没有创建，随后 push 显示无新内容。
- 产生原因：当前命令执行包装层没有按预期保留组合命令中的双引号边界，带空格的提交说明被 Git
  当成了多个文件路径参数。这不是暂存区丢失，也不是远程仓库故障。
- 排查思路：立即检查 `git status` 和 `git log`；六个文件仍处于 staged，HEAD 仍是旧提交，说明
  失败发生在创建 commit 之前，没有产生半完成远程状态。
- 解决方法：先把 commit、push 和状态检查拆成独立 Git CMD 调用；由于独立 commit 中双引号仍被
  包装层破坏，最终使用不含空格但语义等价的提交主题 `feat:integrate-persistent-agent-orchestration`，
  再单独执行 push 和状态复核。
- 学到的知识：自动化 Git 操作也要按状态机复核；命令失败后先确认 HEAD、暂存区和远程关系，
  不能因为后续 push 返回成功就误以为提交已经存在。

- 学到的知识：搜索工具同样存在输入边界；当目标不是正则时，固定字符串模式更可靠。

- 问题现象：6 个行为测试和 mypy 均通过，但 Ruff 报告测试模块导入顺序错误，并指出一行超过

## 第七小阶段：正式 Agent 组合根与 FastAPI 接口

### 本小阶段目标

- 把持久化会话、结构化记忆、只读资产工具和模型 Provider 装配成正式应用服务；
- 让 FastAPI 创建、恢复、删除和继续同一 SQLite 中的会话；
- 在一轮回答成功落库后生成至多一条结构化候选记忆；
- 使用独立 API 查看、确认、拒绝和删除候选，模型不能直接改变长期记忆状态；
- 缺少模型 Key 时保留离线资产、会话和记忆能力，只让聊天入口返回 503；
- 所有自动测试使用 Fake 行情、Fake 模型和临时 SQLite，不消耗真实额度。

### 为什么需要 `AgentApplicationService`

`PersistentToolCallingAgent` 只关心上下文、模型工具循环和整轮消息提交；`MemoryService` 只关心
确定性记忆状态机。如果 FastAPI 路由自己依次调用两者，CLI 将来还要复制同一套流程，异常降级
规则也容易不一致。因此新增应用服务统一表达：

```text
Agent 完成回答并原子保存整轮消息
  → 取刚刚落库的 user 消息作为可信来源
  → 候选抽取器返回无 status、无来源 UUID 的草稿
  → 应用服务补上可信来源
  → MemoryService 校验敏感内容并保存 candidate
```

候选抽取位于回答提交之后，是因为模型已经成功回答这一事实不能被第二次辅助模型调用推翻。若
抽取发生 JSON 错误、超时或连接故障，API 仍返回回答和 `memory_warning`；若主 Agent 本身失败，
则沿用整轮回滚规则，不保存半轮消息。

### 候选抽取协议如何限制模型权限

`MemoryCandidateDraft` 只有类型、键、JSON 值、作用域和可选 TTL，没有 `status`、`version`、
`confirmed_at` 或来源 UUID。`ModelMemoryCandidateExtractor` 使用 `tool_choice=none`、temperature 0
和严格 JSON 根结构，每轮最多一条候选；普通即时问题应返回 `{"candidate":null}`。

系统提示明确排除持仓、行情、收益、交易流水、账号和凭据。这不是唯一安全层：模型 JSON 还会
经过 Pydantic 字段校验，应用服务补可信来源，最后由 `MemoryService` 再验证来源 user 消息和敏感
内容。任何一层都不能直接产生 ACTIVE 状态。

### 一个数据库为什么仍使用两个 Unit of Work

组合根只创建一个 `DatabaseManager`，确保资产面板、账本、会话和记忆确实连接同一 SQLite 文件；
但 Dashboard UoW 只暴露持仓/价格/流水/批次，Memory UoW 只暴露会话/记忆/事件。共享物理连接
配置不等于合并业务事务边界，这使 Agent 读取资产时仍必须通过只读工具，而不能绕过 Service
直接拿到所有 Repository。

模型 Provider 则由主 Agent、滚动摘要器和候选抽取器共享，避免每个适配器各建连接池。关闭顺序
由组合根统一规定：先关闭 Agent 拥有的模型客户端，再关闭行情与数据库资源。

### FastAPI 端点与错误语义

- `/api/v1/agent/sessions`：创建、列出和读取会话；`/{id}/messages` 恢复完整原始轨迹；
- `/api/v1/agent/sessions/{id}/chat`：执行持久化只读 Agent 并返回可选候选；
- `/api/v1/memories` 与 `/candidates`：组合筛选长期记忆和查看待确认项；
- `/api/v1/memories/{id}/confirm|reject`：显式用户状态动作；
- `/api/v1/memories/{id}`：读取或硬删除正文；`/{id}/events` 在正文删除后仍可返回最小审计。

不存在的会话或记忆返回 404；归档、并发冲突和非法状态迁移返回 409；请求/记忆校验返回 422；
模型限流、超时、连接失败分别映射 429、504、503，模型协议或 Agent 无最终回答返回 502。HTTP
错误保持原有 `{"error":{"code":...,"message":...}}` 结构。

## 本阶段问题记录（续）

### 16. Git CMD 包装层再次破坏 `rg` 的引号和管道

- 问题现象：用带括号、空格和管道的复合正则搜索类名时，`rg` 把模式片段解释为文件名并返回
  Windows 路径语法错误。
- 产生原因：命令字符串经过执行包装层和 `cmd.exe` 两次解析，正则中的引号与 `|` 没有按原意
  传给 `rg`。
- 排查思路：确认错误来自搜索命令而不是源码，再改用 PowerShell 单引号承载只读搜索表达式。
- 解决方法：Git 操作仍固定使用 Git CMD；复杂只读源码搜索避免在 CMD 中拼接多层正则。
- 学到的知识：Shell 选择也是输入边界设计，失败的诊断命令不能被误认为代码错误。

### 17. 一个 apply_patch 同时删除并新增同一路径失败

- 问题现象：尝试用同一补丁完整替换 `composition.py` 时，工具报告多个操作指向同一文件。
- 产生原因：补丁同时包含 Delete File 和 Add File，补丁应用器禁止在一次事务内对相同路径声明
  两种文件级操作。
- 排查思路：检查失败发生在补丁校验阶段，因此原文件删除动作也没有部分执行。
- 解决方法：先用独立补丁删除旧文件，再用第二个补丁新增完整内容，随后立即运行 Ruff 和 mypy。
- 学到的知识：原子补丁失败后要先确认工作区状态；大文件替换应使用单个 Update 或分开的
  Delete/Add，不能假设工具会自动合并文件级指令。

### 18. 新增跨模块导入不符合 Ruff 排序

- 问题现象：目标 mypy 通过，但 Ruff 报告 `agents/__init__.py` 和 `web/app.py` 的导入块未排序。
- 产生原因：逐步加入 Agent、模型和记忆异常时，导入顺序不再符合项目统一规则。
- 排查思路：确认只有 `I001`，没有未使用导入或类型错误。
- 解决方法：只对两个目标文件执行 Ruff 自动整理导入，然后重新运行目标检查。
- 学到的知识：跨层组合根很容易积累导入噪声；自动排序适合机械格式修复，但不应借机格式化
  无关文件。
